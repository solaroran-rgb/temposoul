## 2. 需求全景（用户全部诉求，已从多轮对话提取）

### 2.1 视觉/UI 风格要求
1. 整体背景宇宙星云 + 青蓝荧光 HUD 线稿，纯黑，暗色调
2. **俯瞰视角**，人物在画面最下方/中央，极小，由粒子/光效组成，仰望宇宙
3. 下方环境占屏幕约 20%：线稿城市、山河、湖泊、起伏地形，向远处淡化融入星空
4. 星空为主体：清晰星点、极细暗青星座连线、重要星座带标注和素描图案、月亮相位准确
5. 无传统顶栏、无卡片、无蜿蜒光路、无阴天雾、不贴地名标签
6. 左上标题"命律 TempoSoul / 探索命运的节律"，右上按钮组
7. 三阶段认知：第一眼宇宙 → 第二眼自己城市 → 第三眼认出地标

### 2.2 功能要求
1. **IP 定位**：进入时抓 IP，实时渲染用户所在经纬度的星空
2. **真实星空**：按实时时间+经纬度渲染，星位/星座/月亮必须和窗外一致，可截图保存
3. **3D 地图**：按用户位置方圆几十公里渲染线稿地图，含主要建筑、河流、山峰、湖泊，朝北
4. **时间/地点选择**：用户可指定任意地点和时间查看星空
5. **保存图**：可保存全屏高清星空图，或"星空+地图"合成图
6. **探索星空子功能**：每星座带标注、素描图案、说明、与用户的关系关联分析
7. 性能红线：首屏独立分包 gzip 控制在合理范围，不拖慢主站

## 4. 第一阶段：四专家方案输出

> 每位专家只写自己那一章，给出：技术选型、关键算法/数据来源、模块划分、风险与工作量。

### 4.1 ASTRO（天文渲染专家）方案

**目标**：星空与月亮必须真实——"和用户窗外看到的一致，每颗星位置正确，月亮相位正确"。

**星表数据**：
- 数据源：**BSC5Y**（Bright Star Catalog，~1400 颗亮于 6.5 等）——够肉眼可见，体积可控。不直接上 Hipparcos 11 万颗（体积/算力都浪费）。
- 打包：RA/Dec/mag/颜色 压成二进制 Float32Array，单独 chunk，路由懒加载。预估 gzip < 15KB。
- 星座连线：IAU 官方边界线（~88 星座），MVP 先上北半球主要 15 个。

**星位算法**：
- 现有 `astro.ts` 的 JD→恒星时→地平坐标框架正确，需补**岁差/章动小修正**（误差从 ~2° 压到 <0.5°，肉眼不可辨）。
- 不引入 VSOP87/NOVAS（过重）。Meeus 简化公式足够。

**投影**：
- 上半球天球用**等距圆柱投影**：方位角 0–360° 映射屏幕全宽，高度角 0–90° 映射从地平线到天顶的垂直高度。
- 地平线对齐屏幕 78% 处（与 V4 底图的城市天际线吻合）。

**月亮**：
- Meeus《Astronomical Algorithms》简化轨道（~60 行）：算黄经黄纬→地平坐标；相位 = 月球与太阳的夹角，画成对应弦月/满月。
- 2026-09-13 为农历初三蛾眉月，西方低空——正好落在 V4 图月亮位置。

**与静态底图融合策略（关键决策）**：
- **不**全屏重绘（会丢掉 V4 的城市艺术感）。
- 方案：保留 V4 底图的"地面+城市+人物"作为固定下层；把屏幕上 78% 天空区域做成**透明叠加层**，动态渲染真实星点+星座+月亮。
- 风险：底图里 AI 画的假星星要先抹掉（后期处理图天空层为纯黑），否则真假重叠。

**工作量**：星表清洗打包 0.5 天；月亮算法 0.5 天；天空叠加层 1 天。**风险**：星表数据需确认来源许可。

### 4.2 TERRAIN（3D 地图专家）方案

**目标**：下方线稿地形是"用户真实所在城市"，保持 HUD 线稿草图感。

**分两阶段**：

- **MVP（先做）**：程序化伪地形。基于经纬度做确定性噪声（seeded noise），生成起伏山峦+河流曲线+简化城市街区块。不接真实 OSM——先把"俯瞰线稿"的视觉和交互跑通。城市名通过参数注入（济南/北京/...）。
- **P1（后做）**：真实 OSM。CF Function 调 Overpass API，按经纬度方圆 20km 取 `natural=water`（湖泊）、`waterway=river`（河流）、`building`（建筑轮廓）、`natural=peak`（山峰），结果存 KV 缓存（按城市粒度），前端 Canvas 2D 画成荧光线稿。

**渲染技术**：**Canvas 2D**（不碰 WebGL/Three）。2.5D 俯瞰——网格透视，消失点在地平线中央，近大远小。

**风格化管线**：OSM 几何 → 统一描边色 `rgba(80,200,220,α)` → 近亮远淡透明度渐变 → 近粗远细线宽。不填色，纯线稿。

**地标识别**：不贴文字（用户要求）。靠形状认——大明湖是大片不规则水域轮廓，黄河是蜿蜒细线。P1 人工给每个城市标注"地标形状描述"即可。

**工作量**：MVP 伪地形 1 天；OSM 链路（CF+KV+前端）2 天。**风险**：Overpass 免费额度/延迟，必须 KV 缓存。

### 4.3 ARCH（前端架构师）方案

**技术选型结论**：**Canvas 2D 混合方案，不上 Three.js**。
- 理由：星点+线稿地图全是 2D 路径/点，Canvas 2D 足够；Three.js 会让包体 +500KB，违反 74KB gzip 红线。
- 渲染循环：`requestAnimationFrame`，星点用预渲染 sprite（画一次到 offscreen canvas 复用），避免每帧 arc。

**模块结构**：
```
src/lib/sky/
  astro.ts       # 已有，补岁差
  moon.ts        # 新增，月亮轨道
  stars.data.ts  # 二进制星表 loader（懒加载）
  SkyCanvas.tsx  # 天空叠加层
  TerrainCanvas.tsx # 地面/城市层（新）
src/pages/SkyPage/
```

**数据流**：`CF Function /api/geo`（request.cf）→ 返回 `{lat, lon, city}` → SkyPage state → 两个 Canvas 各取所需。

**CF Function**（`functions/api/geo.ts`）：读 `request.cf.latitude/longitude/city`，返回 JSON。无需数据库。

**性能预算**：
- SkyPage 主包 ≤ 10KB gzip
- 星表 chunk ≤ 15KB gzip（懒加载，不阻塞首屏）
- 首屏 LCP：静态底图 < 2s
- DPR 上限 2，星点数 ≤ 1500

**工作量**：0.5 天。**风险**：CF Pages Functions 需确认部署。

### 4.4 VISUAL（产品视觉专家）方案

**构图规格**：
- 地平线（城市/天空交界）：屏幕垂直 **78%** 处
- 星空区：上部 78%
- 地面城市区：下部 22%
- 人物：画面水平居中，垂直在 88% 处，高度占屏 **8%**，发光粒子人形
- 标题：左上 28px 边距；按钮：右上 28px 边距
- 时间滑块：底部 18px 居中偏左

**动效**：
- 入场：整页 1.2s 淡入，星点逐颗点亮（0.8s  stagger），地面从地平线向下渐亮
- 常驻：星点微闪（±10% 亮度，随机相位）；月亮静止
- 视差：鼠标移动时星空层微移（±5px），地面层不动——强化"人站着看天"

**交互**：
- 时间滑块：0–23 点，拖动实时重算星位（不重画底图）
- 全屏星空：隐藏地面层和 UI，纯天空
- 保存图：canvas.toBlob 下载 PNG
- 地点选择：P1 再做（输入框/城市列表）

**星座探索范式**：MVP 不做；P1 做——点击星座名弹出侧栏（暗底毛玻璃），含素描线稿图+说明+与用户命盘的关联。不破坏沉浸感（关闭即回）。

**视觉验收 checklist**：
- [ ] 人物在最下居中，不悬在半空
- [ ] 地面只占 20-22%
- [ ] 星座连线细暗，不喧宾夺主
- [ ] 无阴天雾、无实体山、无蜿蜒光路
- [ ] 星点大小明暗有层次

**工作量**：动效 0.5 天。

## 5. 主审审计意见（v1）

四专家方向基本一致，**无根本性冲突**，但有 3 个必须在 v2 解决的矛盾点：

### 5.1 关键矛盾：静态底图是"一整张 PNG"，无法只换天空
- ASTRO 提议"保留地面层、天空层动态重绘"——但 V4 底图是一张 PNG，城市/人物/星云/星空**已经焊死在一张图里**，边界融合，无法干净剥离。
- **两条路 v2 必须二选一**：
  - **路线甲（分层重绘）**：重新生成一张"纯黑天空 + 线稿城市/人物"的分层底图（城市层单独一张 PNG，天空透明），天空全动态。工作量 +0.5 天，但效果最真。
  - **路线乙（叠加式）**：保留整张 V4 图，只在天空区域叠加**动态亮星点和月亮**，星座线也用图里已有的。改动最小，但星位只是"点"不是"完整星图"。
- 主审倾向**路线甲**，因为用户要的核心就是"星位真实、和窗外一致"，路线乙达不到。

### 5.2 星表与体积
- ASTRO 说 BSC5 ~1400 颗、gzip <15KB。合理。但 ARCH 给 SkyPage 主包 ≤10KB、星表 ≤15KB——**需确认二进制打包格式**（不能用 JSON）。v2 定。

### 5.3 MVP 范围对齐
- TERRAIN 说先用程序化伪地形，ARCH 说先跑通——但用户明确要"真实城市地标"。
- 主审裁定：**MVP 阶段地面仍用 V4 底图（已是好看的线稿城市），不另做程序化地形**；真实 OSM 作为 P1。否则会浪费精力重画一个不如底图的地形。

### 5.4 待 v2 澄清
1. 路线甲 vs 乙
2. 星表二进制格式
3. CF Function 是否已在 Cloudflare Pages 开通（需部署验证）
4. 月亮算法精度是否够用（Meeus 简化版月相误差 <5%，可接受）
