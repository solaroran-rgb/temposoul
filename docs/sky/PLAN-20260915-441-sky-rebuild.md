## 二、审计：三个根因（按影响排序）

### R-A ★ 坐标错配 —— 前 12 批次对拍的是错误对象

| 环节 | 代码事实 | 后果 |
|---|---|---|
| 场景默认坐标 | `SkyScene.ts:48-49` → `curLat=36.65, curLon=117.12`（**济南**） | 默认走济南 |
| 页面默认 | `SkyPage.tsx:68` → `setTimeLocation(now, {lat:36.65, lon:117.12})` | 同上 |
| 真实数据门禁 | `geoEngine.ts:570` → `if (!inTaipei101Tile(lat,lon)) return null;`（半径 3200m） | 济南距台北 ≈1500km → **return null** |
| 静默回退 | `SkyScene.ts:644` → `payload = tp ?? buildLandmarkPayload(...)` | 落到**伪随机天际线**（`buildSolidCity` 程序化生成） |

<span style="color:#39FF14">⇒ 12 个批次优化的全部是「程序化生成的假城市」，而 CT-1 是台北 101 视角的实景基线。对拍对象从第一帧起就错了。</span>

**零成本验证（已执行，未改任何代码）**：访问 `http://127.0.0.1:5210/sky?lat=25.033&lon=121.5654`（`SkyPage.tsx:94-96` 已内建 URL 坐标通道）→ **真实数据立刻生效**：101 塔、350+260 栋真实建筑轮廓、臺北大巨蛋、61 条水系全部出现，零 console error。

### R-B ★ 渲染介质错 —— 线稿 vs 实体暗体

`buildTilePayload()` 把建筑输出为 `lines` + `facades`（**发光线稿**）；而 CT-1 的建筑是**不透明暗体 + 细亮边 + 窗光点**。

仓内其实已有正确介质：`materials/solidCity.ts`（NoBlending + depthWrite + 程序化窗光 + 大气透视），注释里明确写了「换掉 glowFace 是因为加法混合物理上不可能产生遮挡」。**但 tile 路径没有接它** —— `sceneCore` 的 `solid` 槽位只被程序化城市的 `buildSolidCity()` 填充。

### R-C ★ 数据范围不足 —— 覆盖 47%，需要 100%

| 量 | 数值 | 来源 |
|---|---|---|
| 相机 | `PerspectiveCamera(58°垂直, near 2, far 2000)`，pos(0,58,200) → look(0,20,-160) | `SkyScene.ts:109-112` |
| 水平 FOV | ≈88.6°（16:9） | 推导 |
| z≈0 平面横向全宽 | ≈396u | 推导 |
| tile 覆盖 | L0 ±58u / L1 至 ±107u / **L2 只有水系、无建筑** | `config.ts:17-18` + tile 统计 |
| 有效城市直径 | ≈214u → **54%** | 实测 47%，吻合 |
| 原始 OSM bbox | 25.022–25.044 / 121.554–121.577 ≈ **±1.2km** | `data/raw/taipei101-osm.json` |

<span style="color:#39FF14">⇒ 要铺满画面，真实数据需扩到 ±4km 半径，或程序化补足边缘。</span>

## 三、CT-1 规格反解（放大后逐项确认）

放大 `SKY-BASELINE-CT1.png` 地貌区（见 `assets-441/ct1-zoom.png`）后，CT-1 的完整规格：

| 层 | CT-1 实测规格 | 当前 441 实现 |
|---|---|---|
| **建筑介质** | 不透明**暗色实体** + 细亮边轮廓 + 腰线分节 + 稀疏窗光**点** | 发光**线稿团块** ❌ |
| **建筑高度** | 真实高层比例，20–40 层塔遍布 | 矮城（真实 data 多为几十米） ❌ |
| **横向铺满** | **100% 画宽**，密度均匀 | ~47% 中段一块 ❌ |
| **山脉** | 左右两侧**实体山体**，有山脊明暗纹理 | 无（DEM 等高线未成山形） ❌ |
| **地平线** | 连续亮带 + 中心**强放射线**（米字状多条） | 仅弱横带 ❌ |
| **中央法阵** | 人形剪影 + 脚下**多层同心圆** + 光池 | 人形有，法阵弱 |
| **右椭圆环** | 巨大椭圆环（体育场/场馆式，含同心纹） | 无 ❌ |
| **河流** | 右侧波浪形水系贯穿 | 无（数据有，未渲染出） ❌ |
| **月亮** | 暖色弯月，中轴上方 | 无 ❌ |
| **天空** | 星云团块 + 银河 + 星座多边形 | 均匀细星点 ❌ |
| **纵横比** | **1920×969（1.98:1）** | 截图 1920×1080（16:9）⚠️ 口径不齐 |

<span style="color:#39FF14">**判定：CT-1 不是任何真实城市的 1:1 实景还原，而是一张「背光剪影范式」的艺术基线图。**</span>
真实台北数据在几何上做不出「密集高层塔群」—— 101 周边实际是「一塔独秀 + 矮城平摊」。见 `assets-441/cam_A_solid.png`（离线投影，与线上截图形态一致）。

**因此真实数据的正确定位 = 提供街道网格 + 地标锚点（101 / 大巨蛋 / 河流）的可信度；塔群、山脉、放射线必须程序化合成。**

## 四、执行方案（重审后路线）

**策略转变**：从「调参逼近 CT-1」→ <span style="color:#39FF14">「把 CT-1 反解成一组可验证的介质规格，再逐层实现；真实数据作为锚点而非答案」</span>

| 阶段 | 内容 | 成本 | 验收（可判真假） |
|---|---|---|---|
| **P0 坐标归位** | 默认坐标济南→台北 101；或更正确：把「无 tile 数据」从静默回退改为**显式状态**（禁止伪随机冒充真实城） | 0.5h | `/sky` 默认即真实台北；`loadTilePayload` 不再静默返回 null |
| **P1 相机与格式对齐** | 基线口径统一到 1920×969；用离线投影器扫相机（高度 26–95u × 俯角）定标 CT-1 | 1h | 离线 PNG 与 CT-1 的地平线/山位/塔群分布可叠合 |
| **P2 介质切换** | tile 路径接 `solidCity` 实体暗体（`buildTilePayload` 输出 `SolidBox[]`）；建筑=暗体+亮边+窗点 | 2h | 结构像素垂直跨度中位 44.5% → ≥70%（CT-1 74.9%） |
| **P3 铺满** | ① Overpass 拉 ±4km 台北 OSM → 重跑 `build-geo-tiles.mjs` 新增建筑层；② 边缘程序化高层塔群补足 | 3h | 68–100% 区每 10% 列窗口覆盖率 ≥90% |
| **P4 四元素** | 实体山脉（DEM 等高线→山脊剪影）/ **放射线**（CT-1 最强识别特征）/ 暖月 / 右侧椭圆环 | 3h | 左右 15% 列有高于地平线 ≥8% 实体；放射线 ≥12 条；暖色连通域 ≥3 |
| **P5 地面** | 河流 / 路网 / 街区格网 / 法阵多层同心圆 | 2h | 水系可辨；法阵同心环 ≥3 层 |

**建议顺序**：P0 → P2（介质，观感差最大）→ P1/P3 → P4 → P5。
**P0+P2 合计 2.5h 就能拿到「第一次方向正确」的交付**，可先目检再决定是否续跑。

## 六、方法纪律（本批最大产出）

**必须固化的两条：**

1. **每轮必出「同区裁切目检 + 结构指纹表」，均值仅作辅助。** 单看统计量会继续产生假达标。
2. **新增离线投影器 `offline_project.py`（零 WebGL / 零浏览器 / 零新依赖，单次运行 ≈3s）**：
   直接消费烘焙 tile → 针孔相机投影 → 栅格化 PNG。
   **此后所有相机/布局/构图调参先在 Python 里扫参定标，定型后再改 TS** —— 把「改代码→build→起 Chrome→截图」的分钟级循环压到秒级，且不污染 worktree。
