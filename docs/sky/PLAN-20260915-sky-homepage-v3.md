## 0. 结论先行

三句话说完：

1. **前两轮失败不是"审美不够"，是三处规范条文和你给的 CT-1 基线图互相打架。** 执行者选择服从规范，所以越改越"合规"，越改越不像。
2. **判据体系有一个致命结构缺陷：地貌区所有亮度判据只设上限、不设下限。** 唯一安全的策略就是把画面压暗、压少。你看到的"稀疏发光方块"，正是"判据全绿"的**唯一最优解**——不是执行者偷懒，是体系把他推到了那里。

## 1. 诊断：两次失败的真实根因

### 1.1 取证范围

### 1.2 根因一：三处规范条文与 CT-1 打架

| # | 规范原文 | CT-1 的实际 | 执行者的选择 | 后果 |
|---|---|---|---|---|
| ① | §3.1「**禁止**把地平线糊成一条横向连续亮带」 | 地平线辉光带是全画最亮横带（3.2× 天空均亮） | 服从禁令，不做辉光带 | **画面失去唯一的"托底"结构**，天空与地面硬切 |
| ② | §6.6 城市「纯线框 + 窗格点阵，**禁止实体填充**」 | 城市是实体填充插画（V24 实测 36.06，为纯线稿的 3–9 倍） | 服从禁令，只画线框 | **地貌带永远到不了 CT-1 观感**（两轮实测已验证） |
| ③ | §8.3 品牌「**左上**」+ 按钮「**右上**」 | 标题 / 副标题 / CTA 是**顶部中央三段式** | 服从规范，塞进左右上角 | **丢掉首屏视觉中心**，三段式是你参考图的第一眼记忆点 |

<span style="color:#39FF14">这三条不修订，换谁来执行都会失败——因为"正确"的定义和"好看"的定义指向了相反的方向。</span>

### 1.3 根因二：判据体系的最优解悖论（最隐蔽，也最致命）

逐条扫过 V1–V31 中与地貌区/城市有关的判据：

| 判据 | 阈值 | 方向 |
|---|---|---|
| V5 建筑可数性 | ≥ 15 栋 | 下限（但只数轮廓，不看亮度与密度） |
| V23 天空纯黑 | ≥ 88% | 下限（**只管天空**） |
| V24 地貌区均亮 | ≤ L\*40 | **上限** |
| V25 辉光带峰值 | ≤ 地貌均亮 × 0.85 | **上限** |
| V26 塔身表达 | 纯线框 + 窗格点阵 | 定性（禁止实体） |
| V29 单 64×64 块 | ≤ L\*45 | **上限** |

**结论：地貌区连一条"亮度下限"都没有。**

对一个理性执行者，最优策略是：

```
把城市压暗  → V24 ✅  V25 ✅  V29 ✅
把天空留黑  → V23 ✅ （天空只有下限，更黑永远更安全）
把城市做稀  → V5 靠 15 条轮廓就能过 ✅
避免实体    → V26 ✅
```

**31 项全绿，画面是一堆稀疏的青色线框碎片。**

更强的证据：**V24 的阈值 L\*40 是从 CT-1 的 34.82 抄来的，贴着上限。** 即 CT-1 自己离"不合格"只有 5 个点余量，而往下做到 16.58 依然"合格"。约束只堵一边，人就一路往另一边跑。

<span style="color:#39FF14">修法：凡视觉判据必须设双向区间，区间贴着 CT-1 实测值收窄，低于下限同样判失败。见 §6。</span>

### 1.4 根因三：渲染介质的天花板（技术层）

`glowFace.ts`（Y2-甲面片方案）的实际做法：建筑立面三角面片 + `AdditiveBlending` + `uAlphaGate` 钳制 + `depthWrite: false`。

这个组合决定了**它永远画不出实体感**，三个物理原因：

1. **加法混合没有"遮挡"。** `depthWrite: false` 意味着前后楼像素直接相加，不存在"前排挡住后排"。而 CT-1 的城市能"读出"纵深，本质就是遮挡。光会叠加，不会遮挡。
2. **低 α 加法 ≈ 灰。** α=0.1 的青叠在纯黑上仍是暗青，叠十层也就 0.65。它能把画面**变亮**，但变不出"面的密度"。CT-1 城市区均亮 34.82，靠加法叠到那个亮度会先糊成一团。
3. **没有窗光。** §6.6 写着"窗格点阵"，但代码里窗格是 `buildPointsGeometry` 的顶点节点，密度与尺寸远不够。CT-1 里约 60% 的"实体感"来自楼面密密麻麻的窗光。

<span style="color:#39FF14">一句话：现在是"在纯黑上叠很淡的光"，而 CT-1 是"用光堆出一个有厚度、有遮挡、有密度的世界"。这是两种范式，不是两组参数。</span>

## 2. 解构 CT-1：它的"实体感"到底是什么

把 CT-1 的城市放大到像素级看，它的插画质感可以完全拆成五个**可程序化实现**的物理特征（不需要任何位图、贴图、光照）：

| # | 特征 | CT-1 表现 | 当前实现 | 可否程序化 |
|---|---|---|---|---|
| 1 | **遮挡关系** | 前排楼明确压住后排 | 无（加法混合） | ✅ 深度预写 |
| 2 | **自发光梯度** | 街面亮 → 楼顶暗 | 无（亮度均一） | ✅ 顶点局部坐标 |
| 3 | **窗光点阵** | 楼面密布小亮点 | 无 / 极稀疏 | ✅ 片元程序化网格 |
| 4 | **大气透视** | 远景融进辉光带 | 无（远近同亮） | ✅ 深度雾 |
| 5 | **辉光托底** | 地平线全画最亮横带 | 完全缺失 | ✅ 高斯 plane |

**关键判断：这五件事全部能在片元着色器里程序化完成，零位图、零光照、零阴影，依然满足"真实数据驱动 + 纯 WebGL"的红线。**

这就是第四条路——不是原提案"甲/乙/丙"里的任何一条，而是**甲的升级版**：不是简单放宽"禁止实体填充"，而是**用"光的密度场"模拟实体**，从根上绕开"实体材质"的禁令，不用碰 §12 红线。

## 3. 技术方案：光密度体量

### 3.1 核心突破：双 pass 深度预写

整个方案的支点。把建筑拆成两条渲染通道：

**Pass 1 — 深度预写（视觉上几乎不存在）**
- 建筑以**接近纯黑**的颜色渲染（`#01040A` 级），`depthWrite: true`，`depthTest: true`
- 在纯黑星空下，这层**肉眼几乎看不出差异**
- 但它在深度缓冲里建立了**完整的城市前后关系**
- 合规性：它视觉上不可见，不构成 §4.3 所禁的"实体填充面"，只是一个深度结构

**Pass 2 — 光层（视觉的全部）**
- 窗光点阵 + 边缘辉光（Fresnel）+ 自发光梯度，`AdditiveBlending`，`depthTest: true`，`depthWrite: false`
- **因为 Pass 1 已写好深度，后排楼的窗光会被前排楼自动剔除**
- 得到：**视觉上纯粹是光，感知上有完整的前后遮挡与纵深**

<span style="color:#39FF14">这一招同时满足"只准有光"（§4.3）和"必须有实体纵深"（CT-1），是前两轮没找到的那把钥匙。</span>

### 3.2 程序化窗光（密度代差的单点突破）

在片元着色器里用局部坐标生成窗格，**几何成本为零，一栋楼立刻出现几百个窗光点**：

```glsl
vec2  cell = floor(vLocal.xz * uWinCols);
float h    = hash(cell + vSeed);
float lit  = step(1.0 - uLitRatio, h);            // 亮窗比例（约 35%）
vec2  g    = fract(vLocal.xz * uWinCols);
float pane = step(0.22, g.x) * step(0.22, g.y);   // 窗形（留窗棂）
float win  = lit * pane;
```

- `uWinCols` 按建筑在屏幕上的像素宽度自适应（远处楼减小列数，防止糊成一片）
- 这能把城市区亮度从 16.58 推到 CT-1 的 34.82 区间——**不靠调亮线，靠增加光的数量**

### 3.3 自发光梯度 + 大气透视

```glsl
float grad = mix(1.0, 0.18, vLocal.y);                // 街面亮 → 楼顶暗
float fog  = smoothstep(uFogNear, uFogFar, -mv.z);    // 越远越淡
vec3  col  = mix(uColorCity, uColorHaze, fog);        // 远景融进辉光带色
```

### 3.4 几何与性能

- **InstancedMesh** 承载全部建筑（OSM footprint 挤出），单 draw call
- 2000 栋 × ~50 三角 = 10 万三角，远低于现有预算
- 窗光是片元计算，**不增加任何顶点**
- 沿用现有 `TIER` 降级机制：低端档减建筑数 + 关窗光

### 3.5 地平线辉光带（当前完全缺失，必须补）

- 贴地平线的全屏宽 plane，垂直高斯分布 `exp(-((y-y0)*k)²)`，峰值锁定 **y = 68% 画高**
- 水平加噪声调制，避免死板直带
- 目标亮度：天空区均亮的 **3.2×**（对齐 CT-1 实测 24.37 / 7.57）
- 色 `sky-haze` + `cyan-dim` 混合，Additive

### 3.6 人物剪影（当前只剩一个光斑）

CT-1 的人形是**暗剪影被亮辉光托出**——这是**减法**，不是加法：

- 先在地面画一个圆形辉光（Additive）
- 人形用**深色 + NormalBlending** 覆盖上去，它会"吃掉"背后的辉光
- 高 **7.33% 画高**（71px @969），脚底 **98.35%**，中轴 **50%**
- 脚下 12 段磁力环，α ≤ 0.10

## 4. 首页 UI 怎么做（你要的字面答案）

### 4.1 三段式：把视觉中心还给中轴

CT-1 的 UI 是一条**垂直中轴叙事线**：标题 → 副标题 → 按钮 → 月亮 → 中轴光柱 → 人形。这条线是"第一眼信任"的全部。

当前实现把它拆成左上 + 右上两个角，中心空了，所以第一眼看到的是空星空 + 一排发光方块。

| 元素 | CT-1 位置 | 落地规格 |
|---|---|---|
| 主标题「命律 TempoSoul」 | x = 50%，中心 **y ≈ 15.5%** 画高 | 28px / 字距 0.18em / 字重 300 / `#FFFFFF` |
| 副标题「探索命运的节律」 | x = 50%，中心 **y ≈ 21.5%** | 16px / 字距 0.32em / α 0.60 |
| CTA「立即开始」 | x = 50%，中心 **y ≈ 36%** | 玻璃胶囊，padding 10×26 / 14px / 字距 0.12em |
| 月亮 | 右上象限，**不得与人形同轴** | 真实星历，`#F0C878`，≤0.8% 面积，单簇 |

> ⚠️ 上表 y 值为 CT-1 **目测估算（±2%）**。落地前会先用像素探针在 CT-1 原图上实测三条基线，把数字钉死再写 CSS，不靠肉眼。

### 4.2 HUD 收敛（保留 §8.3 的条数，修正它的位置）

- 左上角：**清空**（品牌移到中轴）
- 右上角：只留语言切换等极淡次要入口（α ≤ 0.5）
- 底部：时间滑块（仅 00/23）+ 中央地名
- 三层定位状态指示（GPS/IP/MANUAL）**保留但移到右下角**，不要挂在标题下面

### 4.3 移动端（390×844）

- 竖直百分比全部不变（地平线 574px、人形 62px）
- 水平：只保留中央通道 + 单侧地标
- 标题组字号按现有 media query 缩放（14px / 8px）

### 4.4 立即可做的 P0：1 小时见效，不碰 WebGL

这几条是纯 CSS / 布局，零渲染风险，改完立刻提升第一眼观感——我建议先做这批"给一颗糖"：

1. 品牌块从左上移到中轴（`left:50%` + `transform: translateX(-50%)`）
2. 「立即开始」按钮从右上移到中轴、标题组下方
3. 主标题 28px、字距拉开（当前是压缩态）
4. 副标题提到 16px、字距 0.32em
5. 三层定位指示器移出标题组
6. 清掉左上遗留的 `System/Loc/Time` 面板（若仍在渲染）

> 坑：居中**禁止用 `translate(-50%,-50%)` 配奇数尺寸**（触发半像素整层重采样，历史事故，背景一致率从 53% 掉到 98.89% 的教训）——用负 margin 或 flex 居中。

## 6. 判据补强：从"只设上限"改成"双向区间"

**核心原则：把"不许超过"改成"必须落在区间内"。低于下限与超过上限一样，判失败。**

### 6.1 现有判据修正

| 判据 | 现阈值 | 改为（双向） | CT-1 实测 |
|---|---|---|---|
| V24 地貌区均亮 | ≤ L\*40 | **L\*30 – L\*40**（<30 判失败） | 34.82 |
| V25 辉光带峰值 | ≤ 地貌均亮 × 0.85 | **相对天空区 = 2.5 – 3.9 倍** | 3.2× |
| V29 单 64×64 块 | ≤ L\*45 | ≤ L\*48，**且城市区整体 ≥ L\*25** | 峰值 121 |

### 6.2 新增判据

| # | 判据 | 阈值 | 为什么必须有 |
|---|---|---|---|
| **V32** | 窗光点数 | **≥ 3000**（城市区内亮于 L\*50 的孤立小亮点计数） | 直接把"简笔画"挡在门外 |
| **V33** | 建筑遮挡层数 | **≥ 2**（同一像素列上前后建筑轮廓交叠且亮度不同） | 直接测"纵深"是否存在 |
| **V34** | 品牌标题位置 | 水平中心 50% ± 2%，垂直 ≤ 22% 画高 | 防止再次塞进左上角 |
| **V35** | 地平线辉光带存在性 | 峰值行均亮 **≥ 天空区均亮 × 2.5** | 防止再次被"合规地"删掉 |
| **V36** | 人物可辨识性 | 人形区域与其背后辉光亮度差 **≥ L\*15**（暗剪影特征） | 防止再退化成"一根亮白立柱"/光斑 |
| **V37** | 地标可辨识（强化 V22） | ≥ 3 类，且**山脊在行扫描中有 ≥ 2 个亮度峰** | 防止"山脊存在但看不见" |

## 8. 风险与红线核对

| 风险 | 概率 | 缓解 |
|---|---|---|
| 双 pass 在低端设备 / WebGL1 上表现异常 | 低 | 沿用 `TIER` 降级；异常时退化为单 pass |
| 窗光密度推高 GPU 负载 | 中 | 窗光是片元计算、零几何增量；high/mid/low 三档实测压测 |
| 辉光带过亮反而拖垮 V24 | 中 | 辉光带计入地貌区亮度，与城市亮度联动调参 |
| 再次掉进"判据全绿但难看" | 中 | 每阶段对拍图先给你看，不过目不进下一阶段 |
| 修订 §6.6 触碰红线 | — | 双 pass **不引入**光照 / 阴影 / 位图纹理，逐条比对 §12 红线条文通过 |

**红线核对（一条不碰）**：❌ 不用 AI 生图整图 / 局部位图｜❌ 不引入外部光源、阴影、明暗立体、贴图材质｜❌ 不破坏真实星空 5044 颗 / 星座中文标签 / 真实月相 / DEM 山脊 / 渐进时序 / 三层定位｜❌ 未验收不部署线上、不提交主仓。

**唯一需要重新定义边界的**：§4.3「禁止实体填充面」——本方案的"实体感"完全由**光**（窗光点阵密度 + 遮挡关系 + 透视雾）构成，没有任何填色块、没有贴图、没有光照计算。它不是"填了一个面"，而是"很多光叠在一起，看起来有厚度"。
