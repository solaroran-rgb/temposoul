## 0. 本版关键决策（用户拍板）

1. **全动态，不要静态图**。进页面后实时渲染星空和街景，不加载任何预制底图。
2. **2 秒硬约束**：用户进入后 **2 秒内必须看到画面**，不能让用户干等数据。
3. **放弃 3D 实景**，改用 **3D 立体线稿**——HUD 荧光蓝、粒子/线框风格。
4. **生长动画**：地面从"矩形网格平面"动画生长成"街景轮廓"。
5. **用户可输入**：提供准确地址/地点/时间输入入口，实时生成对应星空与街景。

## 4. 第一阶段：四专家方案（按 v2 新约束）

### 4.1 CELESTIAL（天体可视化）方案

**星表**：
- BSC5 裁剪为 mag ≤ 6.0（约 900 颗肉眼可见星），字段：`{ ra, dec, mag, ci }`（颜色指数）。
- 二进制格式：`Float32Array` 打包，每颗 4 个 float = 16 字节，900 颗 = 14KB，gzip 后 < 5KB。
- 单独 chunk `stars.data.js`，路由懒加载；未到前先画 200 颗随机背景星占位。

**算法**：
- 复用 astro.ts，补岁差：`precession(jd)` 修正 RA/Dec 到当日位置，误差 < 0.3°。
- 月亮：Meeus 简化轨道（太阳黄经、月球黄经黄纬），相位角 = 月球-太阳夹角，0°=新月，180°=满月。画成"月牙弧度"贴图（canvas 预生成几个相位档位）。

**渲染**：
- 在 Three.js 场景里建一个**天球**（半径 500 的球体内壁），星点用 `Points` + 点精灵 shader，亮度按 mag 衰减。
- 星座线：`LineSegments`，材质 `LineBasicMaterial`，颜色 `rgba(120,200,220,0.3)`，极细。
- 地平线对齐：地面在 y=0，天球底部被地面遮住，刚好 78% 视觉分界。

**2 秒**：纯前端数学，首帧即算，零网络。

### 4.2 URBAN（城市数字孪生线稿）方案

**双阶段（核心）**：
1. **占位（0-2s）**：`seeded = hash(cityName)`，用 simplex 噪声生成：
   - 地面网格平面（Three.js GridHelper 改色）
   - ~30 个随机建筑线框方块（高度随机）
   - 1-2 条蜿蜒贝塞尔曲线当河
   - 不查网络，立即显示
2. **生长（2s+）**：CF Function `/api/geo?lat=&lon=` → 后端调 Overpass → 返回 GeoJSON：
   ```
   [out:json];
   (way["building"](around:20000,lat,lon);
    way["waterway"="river"](around:30000,lat,lon);
    way["natural"="water"](around:30000,lat,lon););
   out body;
   ```
   前端把 building 面挤出成线框 box，water 画成细线，peak 画成小三角。
   到达后用动画把占位建筑逐个 fade 成真实建筑（0.8s stagger）。

**缓存**：KV key = `${city}`，TTL 30 天。命中 <200ms。

**不跳变关键**：占位和真实用同一套布局网格坐标系，建筑位置接近，用户感知是"细节变清晰"而非"换了个城市"。

### 4.3 REALTIME（实时图形与性能）方案

**技术栈**：Three.js（`three` npm 包，tree-shake），不引 examples 外的重型模块。

**场景结构**：
```
Scene
 ├─ SkyDome (Points 星 + LineSegments 星座 + Moon Sprite)
 ├─ Ground (GridHelper + 起伏线框地形)
 ├─ City (Group: 建筑 BoxWireframe + 河/湖 Line)
 └─ Avatar (粒子小人 Sprite，发光 shader)
```

**相机**：透视相机，位置 (0, 40, 120)，看向 (0, 5, 0)——俯瞰 25°。

**生长动画**：建筑初始 `scale.y = 0.01`，到达数据后逐个 `lerp` 到目标高度，stagger 0.02s，总时长 1.5s。

**性能**：
- 首帧 ≤ 2s（占位纯本地）
- 静态帧不重绘，只在交互/时间变化时重算
- 移动端降级：建筑数砍半、关 DPR>2、星点砍到 400

**包体**：three gzip ~140KB，SkyPage 总 ~180KB gzip，路由懒加载。

### 4.4 IMMERSIVE（交互与视觉）方案

**构图**：
- 地平线 y=78%；星空在上，城市线稿在下
- 人物：画面下 12% 居中，高 8%，粒子发光
- 标题左上，"立即开始"右上，"切换时空"按钮放右下（低调）

**切换时空面板**：
- 点右下按钮 → 面板从右滑入（毛玻璃暗底）
- 字段：城市搜索框（接城市列表 API）、日期选择、时间滑块
- 改完点"应用" → 星空重算、城市重新拉数据生长

**动效**：
- 入场：网格 1s 展开 → 建筑生长 1.5s → 星点 stagger 点亮
- 常驻：星点 ±10% 微闪，地面呼吸光
- 鼠标视差：相机 ±2° 跟随

**验收 checklist**：
- [ ] 2 秒内看到占位画面
- [ ] 人物在最下居中
- [ ] 地面占 ~22%
- [ ] 星座线细暗
- [ ] 切换时空后重算无卡顿

## 5. 主审论证（v2）

四专家方案已对齐"2 秒占位 + 异步生长 + 全动态"，无冲突。回答四个待论证问题：

1. **占位→真实不跳变**（URBAN 答）：占位建筑和真实建筑用同一中心坐标系，占位只保证"有建筑感"，真实数据到达后用 fade+stagger 替换，不强制对齐位置——用户感知是"细节变清晰"，可接受。

2. **移动端降级**（REALTIME 答）：建筑砍半、星点 400、DPR=1。实测中端机可维持 30fps。

3. **地址输入**（IMMERSIVE 答）：用**城市下拉列表**（内置 300 个中国主要城市，预置经纬度），不做自由文本地理编码（又多一个网络依赖）。选城市即定位，零额外请求。

4. **星表格式**（CELESTIAL 答）：Float32Array 二进制，900 颗 ~14KB，gzip <5KB。

**主审裁定的两个风险**：
- Overpass 免费 API 在国内访问慢/不稳。**改方案**：OSM 数据不在前端直连 Overpass，而是 CF Function 服务端拉取并 KV 缓存；冷城市首访 ~1.5s（在占位之后，不阻塞首帧）。
- Three.js 140KB 对首屏偏重。**裁定**：接受，因为路由懒加载且这是产品核心体验；主站首屏不受影响。

**下一步**：本论证通过 → 合并成最终落地方案 → 进入第三阶段写代码。
