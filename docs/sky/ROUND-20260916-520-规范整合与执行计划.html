目标画面根本没有近白像素（p99.9 ≈ 164），城市是「亮而不爆」：均值高（35.27）、尾部低。480 批做成相反的形态 —— 均值偏低（28.60）但尾部极高（235），即「大面积偏暗 + 少量爆亮硬核」。

这条直接定义了 Glow 的正确做法：靠「面」亮起来（大范围中亮度连续结构），不靠「点」爆出来（少数饱和硬核）。柱阵不是「太亮」，是能量分布形态错误（尖峰 vs 平台）。

4.2 老板 V1.0 的审计结果

采纳 12 条：7 层独立控制｜不还原参考图只继承语法｜星空真实天文计算｜地平线辉光是视觉锚点｜城市=高度+轮廓+细线（不需实体）｜权重表（构图★5 / 真实3D★1）｜肌理=地图×星图×线稿×粒子｜数据真实表现艺术化｜小城市三级降级｜双引擎架构｜POC 五问验收

修正 8 条（要点）：

  • M1 「双视点」降级为结果不是核心 —— 拆层后每层只有一个投影假设，不需要「相机」这个概念
  • M2 「粒子」→ 精确为线框 + 稀点光 + Bloom（实测 ⑦⑧ 共 46.3% 是连续结构，非点云）
  • M3 技术栈 Three.js → 阶段 0 用不上（引入 3D 引擎会重现卡死机制）
  • M4 「Glow 宁可弱」→ 弱的是半径不是结构亮度；目标是「亮而细」不是「暗而糊」
  • M5 「天空 50–60%」→ 与 CT-1 冲突，裁定 CT-2 = 57 ± 3%
  • M7 「砍掉 GPS」→ 读作「暂不接入」，现有 L1 链路不得删除

驳回 2 条：R1「完全不要星云层」（实测存在，占 1.0%）｜R2「Cesium 完全不可用」（可作离线数据生产工具）
