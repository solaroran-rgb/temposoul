# TempoSoul 首页星空系统 — 地理-灵境渲染引擎 技术方案（POC 台北）

版本：v0.1-poc-taipei · 2026-09-14 · 状态：**方案稿（未部署）**

---

## 0. 一句话方案

> 用真实经纬度 + 真实地理数据（**构建期预处理 Geo Tiles + CDN 缓存 + LOD 分级**）+ 天文算法实时星空，经 Three.js/WebGL 把地理元素（建筑/道路/河流/山脉/地标）程序化转绘为 TempoSoul 线稿美术；**三层定位解耦数据与渲染**，**渐进式首屏 1–3 秒**呈现"属于每个用户此时此地的宇宙 + 城市线稿"。

不依赖任何图片模型，不实时抓取大范围街景，全部 WebGL 程序化渲染。

---

## 1. 总体架构（双引擎 + 三层 + 一预留）

```
┌─────────────────────────────────────────────────────────┐
│  SkyPage（渐进式渲染编排）                                │
│  0ms 背景 → 300ms 粒子 → 800ms 星空/轮廓 → 1.5s 山河 → 3s 地标 │
└──────────────┬──────────────────────────┬───────────────┘
        ┌───────▼────────┐        ┌────────▼────────┐
        │ 定位层（三层）   │        │ 渲染层           │
        │ GPS → 设备 → IP │        │ Three.js + WebGL│
        │ （解耦，不阻塞） │        │ Shader 粒子/线稿 │
        └───────┬────────┘        └────────┬────────┘
        ┌───────▼─────────────────────────▼────────┐
        │ 数据层（与渲染解耦，引擎只消费经纬度）        │
        │ 天文引擎：星位/星座/月相（实时计算，已有）     │
        │ 地理引擎：Geo Tiles → 线稿坐标（预生成，新增）│
        └───────┬────────────────────────────────────┘
        ┌───────▼────────┐
        │ 命理数据层（预留）│ → 星盘/运势叠加（未来）
        └────────────────┘
```

- **天文引擎**（已有，完整复用）：`src/lib/sky/` —— 岁差、恒星时、赤经赤纬→地平坐标实时计算；星点 GLSL 粒子；星座连线与标签；月相。**用户看到的星空 = 真实天空**（经纬度 + 精确时间，天文算法，与 VPN/IP 无关，最终经纬度一旦确定即重算）。
- **地理引擎**（本次方案核心，新建）：`src/lib/geo/` —— 真实经纬度地标 → 本地 3D 坐标 → GlowSeg 荧光线稿 + PointPart 发光粒子，产出渲染层原生数据格式（CityPayload），直接挂载。
- **定位层**（新建）：三层定位，见 §2。
- **渲染层**（已有 + 扩展）：星空/星座/月相/地面网格/HUD 面板已就绪；新增地理线稿通道（复用现有五槽：lines/points/water/roads/landmarks）。
- **命理数据层**（预留）：引擎按经纬度+时间输出时空上下文，未来在此叠加命理数据层，构成完整 TempoSoul 体验。

## 2. 三层定位（用户规格，逐条落地）

| 优先级 | 来源 | 作用 | 失败/拒绝时 |
|---|---|---|---|
| ① 浏览器 Geolocation（GPS） | `navigator.geolocation`（HTTPS 必需） | 精确坐标（米级）校正场景 | 停留 IP 级 |
| ② 设备能力 | 设备网络/信号等可用信息 | 补充精度 | 回退 IP |
| ③ IP 兜底 | `/api/locate`（Cloudflare 边缘） | **仅加速初始加载**，不阻塞 | 默认观测点 + 手动选城 |

**关键规则（防 VPN 搞崩）**：
- IP 只用于"先有东西看"，**星空永远以最终确定的真实经纬度 + 当前时间计算**——VPN 显示东京但人在台北，IP 阶段先出背景/粒子，GPS 授权后瞬间切换为台北星空与台北地标；拒绝授权则手动选城。
- 定位与渲染解耦：定位未完成不阻塞首屏（背景/粒子先行），定位完成后只触发"重算 + 换地标"，无整页白屏。
- 已落地草稿：SkyPage 三层管线（`?lat=&lon=` 演示参数 → IP → GPS → 手动城市面板），带定位源状态徽标（ACQUIRING / IP CITY-LEVEL / GPS PRECISE / MANUAL）。

## 3. 渐进式首屏时间线（可感知最终效果 1–3 秒）

| 时间 | 呈现内容 | 机制 |
|---|---|---|
| **t=0–300ms** | 宇宙背景 + 粒子环境 | CSS 深空渐变+暗网格（零成本）；WebGL 星尘粒子即刻启动；**不依赖定位** |
| **t≈800ms** | 真实星空 + 观测者轮廓 | 天文算法实时计算星位（后台分片重算）；观测者剪影柔和浮现（**重新设计，见 §8 决策点 D1**） |
| **t=1–1.5s** | 建筑轮廓 + 山河浮现 | Geo Tiles L1/L2 线稿挂载（roads/water/lines 槽） |
| **t≈3s** | 地标线稿基本完整 | L0 地标精细线稿（landmarks 槽 + 暖橙焦点粒子），dip 过渡稳定 |

**实现前提**：
- **Geo Tile 预处理**：地标/建筑/道路/河流/山脉在**构建期**转成线稿坐标 JSON（见 §4），运行时仅按 tile 拉取静态文件，零边缘计算。
- **CDN 缓存**：静态 tile 走 Cloudflare Pages 静态托管/CDN，首屏不等待任何动态请求。
- **LOD 分级**：三级（§4），相机距离联动，远处只画等高线/轮廓带，近处精细。
- **全部 WebGL 渲染**：无图片、无 DOM 拼图。

---

## 4. Geo Tile 预处理 + CDN + LOD（关键工程决策）

**背景约束**：生产在 Cloudflare Pages Free 档，**边缘 CPU 限 10ms**（历史 503 根因之一）——任何"运行时抓 OSM 大范围街景再转线稿"的方案都不可行。

**方案：把计算移到构建期，运行时零计算。**

```
构建期（本地/CI）                          运行时（Cloudflare CDN）
OSM way / 公开坐标 ──► 线稿坐标生成器 ──► tile-<city>-L0.json     ──► fetch 静态文件
  （建筑轮廓/道路/河流/               （经纬度→本地坐标，        tile-<city>-L1.json        （CDN 缓存，
    山脉等高线/地标）                    LOD 三级，<50KB/级）      tile-<city>-L2.json          无边缘计算）
```

- **LOD 三级**：
  - **L0 地标**（近，相机 0–1.2km 内精细）：101 塔尖/总统府/龙山寺等，完整轮廓 + 垂直棱线 + 暖橙焦点粒子
  - **L1 建筑轮廓**（中，1.2–2.2km）：简化 footprint 线框，细线低透明度
  - **L2 山脉/河流**（远，>2.2km）：等高线 + 光晕、河流水线，最淡
- **数据源**：公开合法——OSM way 数据（建筑 footprint/水系/道路）与政府开放数据。**POC 阶段**：内置 14 个台北地标的真实坐标 + 示意级轮廓（管线接口 `Landmark[]` 已预留，替换数据源不改引擎）。
- **容量**：每城 3 级 tile 合计 <150KB gzip；全球主要城市逐城生成，按经纬度范围路由取 tile。
- **扩展路径**：台北 POC → 东京/纽约（第二、三 POC）→ 全球城市 tile 库；同一套引擎，只换数据包。

## 5. 视觉语言规范（TempoSoul 线稿美术）

| 地理元素 | 表现手法 | 渲染槽 |
|---|---|---|
| 建筑 | 轮廓提取 → 粒子线框（细线 + 透明度 + 光晕） | landmarks / lines |
| 道路 | 荧光曲线（青色发光细线） | roads |
| 山脉 | 等高线 + 光晕（多环 + 层次） | lines（far） |
| 河流 | 水线（暗青色） | water |
| 地标 | 更精细（完整轮廓 + 垂直棱线 + 暖橙焦点粒子） | landmarks + points(warm) |

- **交互**：鼠标视差（轻微，阻尼 0.08）+ 粒子呼吸（低频、克制）——**不做游戏 UI 花哨感**，安静、有呼吸感。
- **色彩**（沿用提示词体系）：纯黑底 + 青蓝/电光蓝发光 + 局部单点暖橙（仅地标塔尖），无大面积暖色、无杂色。
- **线稿层级**：GlowLine 材质自带 core 亮线 + glow 光晕双层，满足"线框 + 光晕扩散"全息质感。

## 8. 风险与决策点（需用户拍板）

- **D1 · 观测者"人物轮廓"形态**：用户时间线要求 800ms 出现"人物轮廓"。方案给出两种形态（避免回到粗糙火柴人）：
  - A. **剪影式**：柔和半透明青色剪影（人形轮廓填充 + 粒子边缘），安静、像全息影像
  - B. **极简轮廓线**：单条连续轮廓线（无关节细节），与城市线稿同语言
  - 推荐 **A**（"有呼吸感"更贴合需求描述）
- **D2 · 数据精度**：POC 用示意轮廓（真实坐标 + 简化环）vs 正式接 OSM way 真实 footprint。前者快、稳、容量小；后者真实但需数据治理。建议：**POC 示意 → 台北上线前接 OSM 精化 L0 地标**。
- **D3 · 非台北城市回退**：抽象天际线（推荐，有画面）vs 空地面（极简）。当前草稿已实现抽象天际线。
- **D4 · 移动端策略**：LOD 降级 + 粒子减半 + 关闭视差（保持帧率优先）。
