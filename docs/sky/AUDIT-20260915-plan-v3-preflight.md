## 1. F1 · 深度精度（致命，必须先修）

**实证**：`SkyScene.ts:102`

```ts
const camera = new THREE.PerspectiveCamera(58, 1, 0.1, 2000);
```

near/far = **20000:1**。当前全仓 `depthWrite: false`，深度缓冲从未被使用，所以这个坑一直没暴露。我的方案要打开深度写入 → 精度立刻成为瓶颈。

**算式**（透视深度分辨率近似 `Δz ≈ z² · (1/near − 1/far) / 2^bits`）：

取城市中心距相机约 **362 units**（相机 `(0,58,200)` → `lookAt(0,20,-160)`）：

| 配置 | 24-bit 深度 | 16-bit 深度（移动端常见） |
|---|---|---|
| **现状** `near=0.1 / far=2000` | 0.078 units | **20.0 units** ❌ 建筑大规模 z-fighting |
| **建议** `near=2.0 / far=2000` | **0.0039 units** | **1.0 unit** ✅ |

**为什么只改 near、不动 far**：动 far 会裁掉星穹（星点球半径未知），风险不可控；只提近平面可获得 **20 倍精度提升**且零裁剪风险。

**安全性核查**：最近的可见物体距相机 ≥ 60 units（城市半径 `MAX_RADIUS_U=170`，相机 `z=200,y=58`），`near=2.0` 绝对安全。

> ⚠️ 落地前还需实测星穹球半径确认 `far=2000` 足够，这是 **S0 阶段的验证项之一**。

## 2. F2 · 深度语义变更的副作用（必须逐对象处理）

打开城市层 `depthWrite: true` 后，**凡是渲染在其之后且 `depthTest: true` 的对象，可见性会被重新裁决**。

现有状态全表（`grep depthWrite/depthTest` 实证）：

| 对象 | 文件:行 | depthTest | 加深度层后的风险 |
|---|---|---|---|
| `glowLine` 全层 | glowLine.ts:131 | **true**（默认） | 会被建筑挡（多数为期望行为） |
| `glowPoint` 全层 | glowPoint.ts:109/149 | **true**（默认） | 同上 |
| `glowFace` 立面 | glowFace.ts:88 | **true** | 同上 |
| Sprite（标签/月） | SkyScene.ts:148 | **false** ✅ | 无影响 |
| 人形底层 | SkyScene.ts:214 | **false** ✅ | 无影响 |
| 人形粒子 `silPts` | SkyScene.ts:285 区域 | 需确认 | **⚠️ 高危**：若为正，且中轴附近有建筑，人形会被吃掉 |
| 地面网格 `ground` | SkyScene.ts:475 | 需确认 | 中风险：地面会被城市压住 |
| 浮尘 `dust` | SkyScene.ts:465 | 需确认 | 中风险 |

**必须的处置清单**：
1. **人形 `silPts` 显式 `depthTest: false`** —— 人形在中轴底部，CT-1 要求它永远可见，不能被任何建筑裁掉
2. **地面网格、浮尘显式 `depthTest: false`** 或确保渲染于城市之前
3. 星点、星座保持 `depthTest: true`（星星被地平线以下建筑遮住是物理正确，且 §5.4 已有地平线淡出）

> 这条如果漏掉，最可能出现的症状是：**人形随机消失**。这是最容易被误判为"玄学 bug"的一类。

## 3. F3 · 真实 OSM 地基：确认存在（好消息）

原方案最大的假设是"能拿到建筑 footprint 面"。**已证实成立**：

- `geoEngine.ts:305` — `landmarks[].ring?: [number, number][]` ✅ **建筑轮廓多边形存在**
- `geoEngine.ts:368` — `mRingWallsToTris()` ✅ **已有从 ring 生成墙体三角的现成函数**（可复用，不必重写）
- `SkyScene.ts:615` — `loadTilePayload()` 优先消费真实 OSM tile，失败才 fallback 到手工地标 ✅ **真实数据链路是主线**

**派生常量**：`METER_TO_U = 170/3500 ≈ 0.0486`、`HEIGHT_SCALE = 1.8`、`HEIGHT_CAP_U = 60`。

## 3.1 F4 · 但缺屋顶面（我的方案会踩）

`ringWallsToTris()` **只生成 4 面侧墙，没有任何屋顶盖**（`geoEngine.ts:59-66` 实证）。

相机在 `y=58` **俯视** → 现有 `side: THREE.DoubleSide` 会让你看到盒子**内壁**。当前低 α 面片下不明显，一旦我提高体量密度，**这就是明确的视觉 bug**。

**修正**：必须补 roof cap（对每个 ring 做扇形三角化 / `THREE.ShapeUtils.triangulateShape`），或改为 `side: FrontSide` 并保持绕序一致。**推荐补屋顶**（成本极低，且能让俯视角下的体块完整）。

## 4. F3 重估 · 尺度：我推翻了自己的初步判断

我一度认为"真实比例下普通楼仅 2.5px，程序化窗光无意义，方案崩了"。**精算后这个判断是错的**，修正如下：

`METER_TO_U=0.0486`, `HEIGHT_SCALE=1.8` → 普通楼（默认 12m）= **1.049 units**

但透视距离差异极大（城市横跨 `z ∈ [-170, +170]`，相机 `z=200`）：

| 位置 | 距相机 | px / unit | 普通楼 12m 屏幕高度 | 台北 101 (508m) |
|---|---|---|---|---|
| 城市**近端** | ~65 u | 14.1 | **14.8 px** ✅ | 660 px |
| 城市**远端** | ~372 u | 2.35 | 2.5 px ❌ | 104 px |

**结论：不是全线崩溃，而是强烈的近远分化 → 用 LOD 分层解决，不必动 `HEIGHT_SCALE`。**

| LOD | 距离 | 屏幕高 | 渲染策略 |
|---|---|---|---|
| **LOD0** | < 120 u | > 8 px | 完整窗光（`uWinCols` 按屏幕像素自适应）+ 边缘 Fresnel |
| **LOD1** | 120–250 u | 3–8 px | 简化窗光（2–3 列）或仅底/顶光带 |
| **LOD2** | > 250 u | < 3 px | 纯渐变体 + 大气雾，靠**数量**形成光海 |

> 附带价值：LOD2 压矮远景，正好规避 `HEIGHT_SCALE` 历史上从 4→1.8 的旧权衡（"塔过高遮挡山脊天际线"），**保住 V37 山脊可辨识**。

## 5. F5 · 判据数学冲突（我方案自带的内部矛盾）

### 5.1 V1 全画纯黑 ≥62% → **城市覆盖率上限 78.9%**

```
天空区 68% × 纯黑 88%  = 59.84%
地貌区 32% × 纯黑率 r  = 需补足 ≥ 2.16%
→ r ≥ 6.75%
```

设城市发光元素占地貌区面积 X，则 `0.32 × (1−X) ≥ 6.75%` → **X ≤ 78.9%**。

<span style="color:#39FF14">推论：CT-1 中央那条 30% 宽的暗通道，在功能上是"负空间配额"，不是装饰。删掉它必然违反 A1。</span>

**约束**：城市必须留黑缝，禁止无脑密铺。这是我方案必须内建的硬约束（Emitter 端密度上限）。

### 5.2 V23（天空纯黑 ≥88%） vs 我新增的 V35（辉光带 ≥天空均亮×2.5）

辉光带越强，向上^{(天空侧)}的尾巴越会抬亮天空底部，直接压低 V23。

**修正：辉光带必须非对称分布**：

| 方向 | σ | 效果 |
|---|---|---|
| 天空侧（向上） | **小**（快速衰减，近似截断） | 保住 V23 天空纯黑 |
| 地貌侧（向下） | **大**（缓慢衰减） | 达成"托住画面"的视觉 + V25/V35 |

> 参考：CT-1 概念图层自己天空纯黑只有 **72.4%**，而 WebGL 目标态要求 88%（规范 §4.2 推导）。**辉光带做得和 CT-1 一样强，反而可能判 V23 失败** —— 非对称衰减是唯一解。

## 6. F6 · 自我降级：双 pass → 单 pass

**我审计自己的结论：原方案的"双 pass 深度预写"是过度设计。**

原因：既然 Pass1 输出的是近纯黑色 body 且要写深度，完全可以把它和窗光合成到**同一次着色**里：

```
单 pass:  blending = NoBlending, depthWrite = true, depthTest = true
          fragment color = mix(bodyDark, winColor, winMask) + fresnelEdge
```

| | 双 pass（原） | **单 pass（修订）** |
|---|---|---|
| 绘制次数 | 2 遍几何 | **1 遍** |
| 排序问题 | 有（Additive/Normal 混合管线） | **无** |
| 深度正确性 | 需两遍配合 | **天然正确** |
| 后续 Additive 层（辉光带/能量线/星尘）被遮挡 | 生效 | **同样生效** ✅ |
| 故障点数量 | 多 | **少** |

后续 Additive 装饰层（地平线辉光带、能量连线、星尘）照常 `depthTest: true` 即可被建筑正确遮挡，**不需要靠 Pass1 去"写深度"**。

**方案 v3.1 = 单 pass 自发光体量 + 可选 Additive 光泽层。** 更简单、更快、更少 bug——这是我这次审计最有价值的产出。

## 8. 是否"最佳、完美、不可替代"？（客观对比，不自吹）

| 候选 | 真实数据驱动 | 零位图 | 可达 CT-1 密度 | 移动端 60fps | 合规 | 工程成本 |
|---|---|---|---|---|---|---|
| **A 光密度体量（v3.1）** | ✅ | ✅ | **~85%** | ✅ | ✅ | 中 |
| B SDF Raymarching 城市 | ❌ 难注入 footprint | ✅ | 95% | ❌ 每像素数十步 | ✅ | 大 |
| C AI 建筑图集 + billboard | ⚠️ 部分 | ❌ 位图 | 95% | ✅ | ❌ **触 §12 红线** | 小 |
| D 纯后处理 bloom/辉光 | ✅ | ✅ | ~55% | ✅ | ✅ | 小 |
| E 保留现状继续调参 | ✅ | ✅ | ~45%（两轮实测天花板） | ✅ | ✅ | 极小 |

**结论：A 是唯一同时落在「真实 OSM 数据驱动 × 零位图 × 可达 CT-1 密度 × 移动端可用」四条约束交集里的方案。** B 失绑真实数据且移动端不达标，C 触碰已两次翻车的 §12 红线，D/E 的密度上限已被实测证否。

但我必须说清楚 A 的**三个真实弱点**，不含糊：

1. **程序化窗光有网格规律性**，不如 AI 插画有机随机。缓解：多尺度噪声 + 逐建筑 hash 种子 + 亮窗比例扰动——能大幅缓解，但不敢打包票与自然 randomness 完全等价。
2. **LOD2 远景靠"数量光海"而非细节**。它的观感上限取决于 OSM tile 在该城市能返回多少栋建筑。**这是本审计唯一未能验证的条目**（未跑真实 tile API），列为 S0 必测项——若某城市 OSM 建筑稀疏（如 <200 栋），需要 fallback 密度补充策略。
3. **异步加载 tile** 期间城市为空，需确保 intro 时序与 FCP 1–3s 不冲突。
