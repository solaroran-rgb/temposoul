# T06 · 买三免一规则引擎 + 权益券模型 · 配置说明

> 版本：2026-09-30.v1 ｜ 代码位置：`src/lib/commerce/promo/` ｜ 单测：`tests/promo-*.test.ts`（44 例全绿）

## 0. 一句话

订单结算时把「规则优惠 + 权益券优惠」算清楚，并把**每一分钱优惠的来路**写进订单，事后可追溯。

## 1. 硬约束（改之前先读）

| 项 | 约定 |
|---|---|
| 金额单位 | **统一「分」（整数）**，展示层自行换算 ¥。禁止浮点单价进引擎 |
| 时间 | 一律由调用方以 `now`（ms）注入，引擎内部**不调 `Date.now()`**，保证可重放 |
| 确定性 | 同价取件按 `index` 升序，无随机、无 `Math.random` |
| 失败兜底 | 规则配置非法 / 券仓异常 → 回退默认配置或跳过券，**绝不阻断下单** |
| 应付下限 | `payable = max(0, subtotal - totalDiscount)`，永不为负 |

## 2. 默认规则口径（⚠️ 业务细节待最终确认）

默认规则 `buy3_get1_free_v1`，定义在 `rules.ts` 的 `DEFAULT_PROMO_CONFIG`：

```jsonc
{
  "id": "buy3_get1_free_v1",
  "name": "买三免一（免最低价 1 件）",
  "enabled": true,
  "priority": 100,
  "stackableWithCoupon": false,
  "condition": {
    "minQualifiedUnits": 3,
    "scope": { "kind": "report", "skus": [], "excludeSkus": [] }
  },
  "action": {
    "type": "buy_n_get_m_free",
    "n": 3, "m": 1,
    "pick": "cheapest",
    "requireSameSku": false,
    "maxFreeUnits": 0
  }
}
```

### 已用单测固定的边界

| 场景 | 结果 |
|---|---|
| 2 件 | 不免 |
| 3 件（990 / 3990 / 8800） | 免最低价 990，应付 12790 |
| 4 件 | 只免 1 件（`floor(4/3)=1`） |
| 6 件 | 免 2 件（最便宜的两件，1980） |
| 同价 3 件 | 免一件 = 单价，按 index=0 取，结果确定 |
| `quantity=3` 单行项 | 按件展开计数，等同 3 件 |
| 订阅类 SKU | 默认**不参与**（scope = report） |

### 三处「待用户最终确认」的默认值

| 待确认项 | 当前默认 | 改成另一口径的入口 |
|---|---|---|
| 适用商品范围 | 仅 `report` 类（订阅 / 服务不参与） | `condition.scope.kind` 改 `all`；或用 `skus` 白名单 / `excludeSkus` 黑名单 |
| 是否必须同 SKU | `requireSameSku: false`（允许跨 SKU、跨报告组合） | 改 `true`：同一 SKU 满 3 才免，3 个不同 SKU 各 1 件不免 |
| 免单与券是否叠加 | `stackableWithCoupon: false`（二选一，取更优惠者） | 改 `true`：先免单，券再按折后金额抵扣 |

> 上方三项均**未经过业务终确认**，先按保守口径落地（适用范围窄、让利可控）。确认后改配置即可，无需改引擎代码。

## 3. 规则配置怎么改（两个入口 + 生效方式）

### 入口 A：代码常量（推荐做基线）

改 `src/lib/commerce/promo/rules.ts` 的 `DEFAULT_PROMO_CONFIG`。
**生效方式：需重新构建 + 部署**（构建期常量）。

### 入口 B：环境变量 `PROMO_RULES_JSON`（推荐做运营热更）

把规则集 JSON 塞进 Worker 环境变量，结算时调用：

```ts
import { resolvePromoConfig, settleOrder } from '@/lib/commerce/promo';

const result = await settleOrder({
  orderId, userId, items, now: Date.now(),
  couponCode, couponStore,
  config: resolvePromoConfig(env.PROMO_RULES_JSON),
});
```

**生效方式：`resolvePromoConfig` 每次调用实时解析、不做进程内缓存 —— 环境变量改完，下一次请求即生效（热更，无需重启进程）**；但 Cloudflare 环境变量本身变更需一次 `wrangler deploy`（不是重启，是重部署）。解析失败 / 结构非法自动回退 `DEFAULT_PROMO_CONFIG`，故障不阻断下单。

### 规则字段说明

**条件 `condition`**（缺省 = 不做该限制）

| 字段 | 含义 |
|---|---|
| `minQualifiedUnits` | 合格商品最少件数，缺省取 `action.n` |
| `minSubtotal` | 订单小计门槛（分） |
| `scope` | 适用域：分类 + SKU 白名单 / 黑名单（黑名单优先） |
| `userTags` | 限定用户标签，命中任一即通过；空 = 不限 |

**动作 `action`**

| 类型 | 字段 | 说明 |
|---|---|---|
| `buy_n_get_m_free` | `n` / `m` | 每满 n 件免 m 件，免单件数 = `floor(合格件数 / n) * m` |
| | `pick` | `cheapest`（免最低价，默认）/ `most_expensive` |
| | `requireSameSku` | `false`=可跨 SKU 组合；`true`=按 SKU 各自成组计算 |
| | `maxFreeUnits` | 单笔免单件数上限，0 = 不限 |
| `percent_off` | `percentOff` | 减免百分比，10 = 减 10%；**向下取整到分**（让利取小） |
| | `applyOn` | `subtotal`（全单）/ `qualified_subtotal`（仅适用域内商品） |
| | `maxDiscount` | 封顶（分），0 = 不封顶 |

**其他**：`enabled` 开关；`priority` 数字小者先应用；多条规则串行，**先命中的规则会占用被免单的件，后续规则不得重复免同一件**（防叠加漏洞，已单测覆盖）。

## 4. 权益券模型

定义在 `types.ts` 的 `Coupon`，字段：

| 组 | 字段 |
|---|---|
| 标识 | `code`（归一化：trim + 大写） |
| 类型 | `type`: `amount_off`（固定金额）/ `percent_off`（折扣，向下取整 + `maxDiscount` 封顶） |
| 有效期 | `validFrom` / `validTo`（ms），**左闭右开 `[from, to)`** |
| 适用域 | `scope`（与规则同构）；`applyOn`: `subtotal` / `qualified_subtotal` |
| 门槛 | `minSpend`（分），按**原价小计**判定，不被规则优惠顶掉 |
| 归属 | `ownerUserId`（空 = 不记名券） |
| 状态 | `status`: `issued` → `used` / `expired` / `revoked` |
| 核销回填 | `usedAt` / `usedByOrderId` / `usedByUser` —— **构成幂等依据** |

### 幂等机制（一张券只能用一次）

- **同一订单重复提交**（网络重试 / 钩子重放）→ 命中 `usedByOrderId === orderId`，返回一致结果，**不二次抵扣**，标记 `idempotent: true`。
- **换订单重复核销** → 拒绝 `already_used`。
- 过期券被惰性标记为 `expired`；已作废 / 未开始 / 非本人 / 适用域为空 / 未达门槛，分别返回对应 reason，**不影响规则优惠正常生效**。
- 结算顺序：**先 `inspectCoupon` 试算，确定要抵扣了才 `redeem` 落库** —— 试算绝不会烧券。命中不可叠加规则且规则更优时，券保持 `issued` 不被消耗。

### 券仓储

`CouponStore` 接口（`get` / `save` / `redeem`）。当前提供 `createInMemoryCouponStore()` 用于单测与本地开发；**生产落库请替换为 D1 / KV 实现（对接 T04 orders 表），引擎侧零改动**。

## 5. 与 T04 orders 表的对接点

T04 落库后，在订单创建 / 结算处调用 `settleOrder`，建议订单表新增以下字段（命名以 T04 最终 schema 为准）：

| 字段 | 来源 | 说明 |
|---|---|---|
| `subtotal` | `result.subtotal` | 原价小计（分） |
| `total_discount` | `result.totalDiscount` | 优惠合计（分） |
| `payable` | `result.payable` | 应付（分），mock 支付阶段用它校验结算金额 |
| `promo_lines` | `result.discountLines` | JSON：逐条优惠的来源 / id / 金额 / 命中 SKU，可追溯 |
| `promo_rule_ids` | `result.appliedRuleIds` | 命中规则 id |
| `coupon_code` / `coupon_discount` | `result.coupon` / `result.couponDiscount` | 券核销记录 |
| `promo_trace` | `result.trace` | 人类可读审计轨迹（排障用） |

**幂等对接**：同一 `orderId` 重复触发结算钩子是安全的（券幂等 + 引擎无状态），建议订单侧仍以 `orderId` 做唯一约束。
